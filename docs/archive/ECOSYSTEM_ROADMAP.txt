## The Ecosystem Gap — Things NOT Part Of The Language Itself
## (Priority ordered — what would immediately boost the language)

─────────────────────────────────────────────────────────────
1. MEANINGFUL ERROR MESSAGES                    [RESOLVED - v5.2]
─────────────────────────────────────────────────────────────
Status: RESOLVED - The compiler reports line and column coordinates for all syntax errors,
rejects invalid condition expressions and missing opening braces, gates execution binary
synthesis upon error, and provides targeted diagnostics:
  - Line / column coordinates on all errors
  - Unrecognized statement keywords
  - Missing '=' in let assignments
  - Undefined function names in call statements
  - Unclosed blocks (missing '}') at EOF
  - Unmatched '}' (no block open)
  - Invalid relational operators / condition expression trap (`if a * a > n`, `if a = 5`)
  - Expected '{' after condition head
  - Output binary gating (app.exe never emitted on failure)

What it should look like:
  code.nex:47:12: error: expected '}' to close 'while' block opened on line 43
  code.nex:102:5: error: undefined variable 'count' (declared vars: counter, total)

Why it matters more than anything else:
  - Features help you build things.
  - Error messages help you when things go wrong — which is MOST of the time.
  - A language people CAN use vs one they WANT to use.

─────────────────────────────────────────────────────────────
2. DOCUMENTATION                                [HIGH]
─────────────────────────────────────────────────────────────
Current state:
  - AI_HANDOFF.md: Written for AI engineers, not users.
  - No language reference.
  - No keyword list.
  - No syntax guide.
  - No tutorial.

What's needed:
  - NEXUS Language Reference (complete keyword + syntax listing)
  - "Hello World to Functions" step-by-step tutorial
  - Built-in operations reference (alloc, load, store, file_*)
  - Known limitations / gotchas (e.g. single-letter variables only right now)

Without docs, nobody — including the developer in 6 months — can use the 
language without reading the compiler source code line by line.

─────────────────────────────────────────────────────────────
3. STANDARD LIBRARY                             [HIGH]
─────────────────────────────────────────────────────────────
Current state:
  - ZERO built-in utility functions.
  - Every program starts from absolute zero.
  - No abs(), no max(), no min(), no string utilities, nothing.

What a minimal stdlib for NEXUS would look like:
  Math:      abs, max, min, clamp, pow (integer)
  Memory:    memcopy, memset, memcmp
  Strings:   str_len, str_copy, int_to_str, str_to_int (once strings exist)
  I/O:       print_str (once strings exist), print_newline, print_hex
  Array:     arr_fill, arr_sum, arr_max, arr_min

Note: Requires Stage 6 string literals before some of these are possible.
      But math/memory utilities can be done RIGHT NOW.

─────────────────────────────────────────────────────────────
4. EDITOR SUPPORT (Syntax Highlighting)         [MEDIUM]
─────────────────────────────────────────────────────────────
Current state:
  - .nex files appear as plain text in every editor.
  - No keyword coloring, no comment highlighting, no structure visibility.

What's needed:
  - A VS Code grammar file (.tmLanguage.json or .tmGrammar) for .nex files
  - Highlights: keywords (let, while, if, else, fn, call, return, print, read,
                alloc, load, store, file_*), numbers, comments (#), operators

Effort: ~1 weekend. Impact: massive psychological difference in writing NEXUS.

─────────────────────────────────────────────────────────────
5. REPL / INTERACTIVE MODE                      [MEDIUM]
─────────────────────────────────────────────────────────────
Current state:
  - Edit code.nex → run nexc.exe → run app.exe → repeat.
  - Minimum 3 steps and ~200ms per experiment.
  - No way to quickly test a one-liner.

What a NEXUS REPL would do:
  - Accept one NEXUS statement at a time.
  - Compile and execute it immediately.
  - Show the result.
  - Maintain variable state between lines.

Architecturally: The REPL wraps the compiler in a loop. Each input gets 
appended to a running program, recompiled, and the new output (if any) is shown.

─────────────────────────────────────────────────────────────
6. BUILD SYSTEM / PROJECT FILES                 [LOWER]
─────────────────────────────────────────────────────────────
Right now compilation is: copy your code to code.nex, run nexc.exe.
As multi-file support (Stage 6) arrives, this becomes unmanageable.

What's needed eventually:
  - A nexus.project file format (JSON or NEXUS-native)
  - A nexbuild.exe that reads it and orchestrates compilation
  - Dependency tracking (only recompile changed files)
